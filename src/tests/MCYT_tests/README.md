# Проверка сервиса на MCYT

Скрипт создаёт эталоны через HTTP API и отдельно проверяет подлинные подписи и целевые подделки из MCYT_Signature_100. Он запускается вручную и не входит в обычный запуск pytest.

## Запуск

Установите зависимости проекта, настройте окружение и запустите сервис. Распакуйте датасет в `data/MCYT_Signature_100`: внутри должны находиться каталоги авторов `0000`, `0001` и т. д. Для доступа используйте API-ключ зарегистрированного интегратора.

Из каталога `src/`:

```bash
export MCYT_API_KEY="<api-key>"
poetry run python -m tests.MCYT_tests.run --base-url http://127.0.0.1:8123
```

Укажите фактический адрес сервиса без `/api/v1`. Ключ также можно передать через `--api-key`.

Проверка отдельных авторов и выбор файла отчёта:

```bash
poetry run python -m tests.MCYT_tests.run \
  --base-url http://127.0.0.1:8123 \
  --authors 0000 0001 0002 \
  --output ../data/mcyt_results/selected.json
```

Другой путь к датасету задаётся через `--dataset`, тайм-аут одного запроса — через `--timeout` в секундах. По умолчанию проверяются все авторы, тайм-аут равен 30 секундам, отчёт сохраняется в новый файл `data/mcyt_results/<run_id>.json`. Явно указанный `--output` перезаписывается.

Каждый запуск создаёт эталоны с новыми `subject_id` вида `mcyt:<run_id>:<author_id>`. Они остаются у владельца API-ключа после прогона; UUID сохраняются в отчёте.

## Разделение данных

Для каждого автора файлы сортируются по имени:

- `v00`–`v09`: десять подлинных образцов для создания эталона;
- `v10`–`v24`: пятнадцать других подлинных образцов для проверки;
- `f00`–`f24`: двадцать пять целевых подделок для проверки.

Регистрационная и проверочная выборки не пересекаются. Для полного MCYT_Signature_100 получаются 100 эталонов, 1500 проверок подлинных подписей и 2500 проверок подделок.

FPG читается по формату поставляемого с датасетом `FPG_Signature_Read.m`: сохраняются координаты, азимут и наклон; давление делится на 1023; время вычисляется по индексу точки и частоте из заголовка. Точки с нулевым давлением сохраняются. Нормализацию и формирование эталонов выполняет сервис.

## Результаты

- **FRR, ложные отказы** = отклонённые подлинные подписи / успешно проверенные подлинные подписи × 100%.
- **FAR, ложные допуски** = принятые подделки / успешно проверенные подделки × 100%.

Решение берётся из `validated`, оценка — из `score`, без собственного изменения порога. Таким образом измеряется поведение запущенной версии сервиса. Подбор весов и порога этот скрипт не выполняет.

JSON содержит перечень авторов, регистрационные файлы, UUID эталонов, каждый проверочный файл с `score` и `validated`, ошибки и общие показатели. API-ключ в отчёт не записывается. Отчёт обновляется после каждого автора.

HTTP-ошибки, ошибки чтения и некорректные ответы учитываются отдельно и не считаются биометрическими отказами или допусками. При ошибке создания эталона проверки этого автора пропускаются. Если оценённых образцов нет, соответствующий показатель равен `null`. При неполном прогоне `complete=false`: значения FRR/FAR относятся только к полученным решениям.

Код завершения `0` означает завершённый прогон без технических ошибок независимо от качества распознавания. Код `1` означает техническую ошибку или неполный прогон.

Датасет и отчёты остаются локальными. В Git из каталога `data/` добавляется только `.gitkeep`.
