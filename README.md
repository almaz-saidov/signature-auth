# signature-auth

API для биометрической проверки по динамике рукописной подписи. Интегратор передаёт десять образцов для создания эталона, а затем сравнивает с ним новые подписи.

Учётная запись интегратора предоставляет доступ к API. Пользователь вашего приложения обозначается строковым `subject_id`: например, `"42"`, `"customer-123"` или UUID в виде строки. Управление пользователями, паролями и сессиями вашего приложения остаётся на вашей стороне.

> Доступны регистрация интегратора, проверка и перевыпуск API-ключа, создание и замена эталона, получение списка и метаданных эталонов, удаление эталонов и проверка новой подписи.

## Подключение

Адрес сервиса предоставляет его владелец. Все пути ниже указаны относительно этого адреса.

- Базовый путь API: `/api/v1`.
- Интерактивная документация: `/docs`.
- Спецификация OpenAPI: `/openapi.json`.
- Тела запросов и ответов: JSON. Для запросов с телом передавайте `Content-Type: application/json`.

Порядок работы:

1. Зарегистрируйте учётную запись интегратора и сохраните выданный API-ключ.
2. Соберите десять образцов подписи пользователя вашего приложения.
3. Отправьте образцы и его `subject_id`, сохраните UUID полученного эталона.
4. Для проверки отправьте новую подпись на сравнение с этим эталоном.
5. Используйте результат сравнения в логике вашего приложения.

## Доступ по API-ключу

Регистрация выполняется без ключа. Для остальных операций требуется заголовок:

```http
Authorization: Bearer <api_key>
```

Одна учётная запись интегратора имеет один действующий ключ. Он возвращается только при регистрации и перевыпуске — сохраните его из ответа. После перевыпуска прежний ключ перестаёт действовать.

Интегратор может работать только со своими эталонами. Доступные эталоны определяются по API-ключу. Для чужого и отсутствующего эталона возвращается одинаковый ответ `404`.

## Операции API

| Метод | Путь | Назначение | Успешный статус |
| --- | --- | --- | --- |
| POST | `/api/v1/users` | Регистрация интегратора | 201 |
| POST | `/api/v1/users/me/api-key` | Перевыпуск API-ключа | 200 |
| POST | `/api/v1/signature-references` | Создание или замена эталона | 201 / 200 |
| GET | `/api/v1/signature-references` | Список своих эталонов | 200 |
| GET | `/api/v1/signature-references/{reference_id}` | Метаданные эталона | 200 |
| DELETE | `/api/v1/signature-references/{reference_id}` | Удаление эталона | 204 |
| POST | `/api/v1/signature-references/{reference_id}/verifications` | Сравнение подписи с эталоном | 200 |

`reference_id` — UUID эталона, полученный при создании или из списка эталонов.

### Регистрация и перевыпуск ключа

`POST /api/v1/users` принимает непустое уникальное имя интегратора:

```json
{
  "username": "example-integrator"
}
```

Ответ содержит API-ключ в поле `api_key` и метаданные учётной записи. Сохраните ключ для последующих запросов. Занятое имя приводит к `409`.

`POST /api/v1/users/me/api-key` требует действующий ключ и не принимает тело запроса. Ответ содержит новый `api_key` и `api_key_created_at`.

### Создание или замена эталона

`POST /api/v1/signature-references` принимает объект с полями:

| Поле | Значение |
| --- | --- |
| `subject_id` | Непустая строка — идентификатор пользователя в вашем приложении |
| `samples` | Массив ровно из десяти образцов в формате, описанном ниже |

Для одного `subject_id` у интегратора хранится один актуальный эталон. Повторная отправка заменяет его. Одинаковые `subject_id` у разных интеграторов независимы. При ошибке обработки образцов предыдущий эталон сохраняется.

При создании возвращается `201`, при замене — `200`. В обоих случаях тело ответа содержит UUID в виде JSON-строки:

```json
"019a1b2c-3d4e-7000-8000-123456789abc"
```

### Получение и удаление эталона

`GET /api/v1/signature-references/{reference_id}` возвращает метаданные:

```json
{
  "id": "019a1b2c-3d4e-7000-8000-123456789abc",
  "subject_id": "customer-123",
  "created_at": "2026-10-25T10:00:00Z",
  "updated_at": "2026-10-25T10:00:00Z"
}
```

Содержимое эталона через API не выдаётся.

`DELETE /api/v1/signature-references/{reference_id}` удаляет эталон и возвращает `204` без тела ответа. Отсутствующий или чужой эталон даёт `404`. После удаления эталон больше не возвращается в списке; получение его метаданных и повторное удаление возвращают `404`.

### Список, пагинация и фильтры

`GET /api/v1/signature-references` принимает необязательные query-параметры:

| Параметр | Назначение | Ограничения и значение по умолчанию |
| --- | --- | --- |
| `subject_id` | Точное совпадение идентификатора | Непустая строка |
| `from` | Начальная дата создания эталона | `YYYY-MM-DD`, включительно, UTC |
| `to` | Конечная дата создания эталона | `YYYY-MM-DD`, включительно, UTC |
| `page` | Номер страницы | От 1; по умолчанию 1 |
| `size` | Число записей на странице | От 1 до 100; по умолчанию 20 |

Пример запроса:

```http
GET /api/v1/signature-references?subject_id=customer-123&from=2026-10-01&to=2026-10-31&page=1&size=20
Authorization: Bearer <api_key>
```

Дата `from` не должна быть позже `to`, иначе возвращается `422`. Граница `to` включает весь указанный день. Порядок выдачи — по дате создания и UUID по убыванию.

Ответ содержит `total`, `page`, `size` и `data`. `total` — число эталонов после фильтрации, до пагинации; `data` — массив метаданных. Если указанная страница выходит за пределы результата, возвращается `200` с пустым `data` и действительным числом `total`. Пример результата без подходящих эталонов:

```json
{
  "total": 0,
  "page": 1,
  "size": 20,
  "data": []
}
```

### Сравнение подписи

`POST /api/v1/signature-references/{reference_id}/verifications` принимает объект с полем `sample`, содержащим один образец подписи.

Ответ содержит:

| Поле | Тип | Значение |
| --- | --- | --- |
| `validated` | boolean | `true` при `score >= 75`, иначе `false` |
| `score` | number | Степень соответствия в процентах, от 0 до 100 |

Пример ответа:

```json
{
  "validated": true,
  "score": 88.4
}
```

Несовпадение возвращается как `validated: false` со статусом `200`; значение `score` также присутствует. Решение принимается без предварительного округления оценки. Интегратор может использовать собственный порог независимо от `validated`.

`score` — степень соответствия эталону, а не вероятность подлинности. Проверка не изменяет сохранённый эталон. Непригодный образец даёт `422`; чужой или отсутствующий эталон — `404`.

Если версия эталона больше не поддерживается, сервис возвращает `422` с сообщением «Версия сохранённого эталона не поддерживается. Обновите эталон.». Для замены отправьте десять новых образцов и прежний `subject_id` в `POST /api/v1/signature-references`, затем повторите проверку.

## Формат образца подписи

Каждый элемент `samples` и значение `sample` — объект с массивом `points`. Все шесть полей каждой точки обязательны:

| Поле | Значение |
| --- | --- |
| `x` | Координата X в исходных единицах устройства |
| `y` | Координата Y в исходных единицах устройства |
| `pressure` | Давление в диапазоне от 0 до 1; 0 означает отсутствие контакта пера |
| `azimuth` | Азимут пера в градусах |
| `altitude` | Угол подъёма пера в градусах |
| `time_ms` | Время от первой точки образца в миллисекундах, неотрицательное |

Пример тела запроса для сравнения. Три точки показывают структуру данных; в рабочем запросе передавайте полную запись подписи:

```json
{
  "sample": {
    "points": [
      {"x": 2100.0, "y": 3400.0, "pressure": 0.12, "azimuth": 180.0, "altitude": 60.0, "time_ms": 0.0},
      {"x": 2103.0, "y": 3405.0, "pressure": 0.13, "azimuth": 181.0, "altitude": 60.0, "time_ms": 10.0},
      {"x": 2107.0, "y": 3408.0, "pressure": 0.14, "azimuth": 182.0, "altitude": 60.0, "time_ms": 20.0}
    ]
  }
}
```

Ограничения:

- В одном образце должно быть не менее двух точек.
- Числовые поля передаются JSON-числами. Строки с числами, `NaN` и бесконечности не принимаются.
- Время первой точки равно нулю. Дальше время не убывает. Внутри штриха точки с одинаковыми временем и координатами объединяются с сохранением последнего измерения; разные координаты при одинаковом времени дают `422` при создании эталона и проверке подписи.
- Неизвестные поля в объектах запросов не принимаются.
- Координаты X и Y должны использовать одинаковые единицы измерения; для эталона и проверяемой подписи используйте совместимый способ записи. Сервис самостоятельно нормализует положение и размер подписи с сохранением пропорций.
- Точки с нулевым давлением сохраняйте: они разделяют штрихи. Азимут не ограничен диапазоном 0–360°.
- Для создания эталона и проверки подписи каждый образец должен содержать движение пера во время контакта и хотя бы один штрих с тремя точками с различным временем. Образцы без контакта, с нулевым размером или неопределимым средним азимутом дают `422`.
- Время передавайте без удаления пауз между штрихами.

### Подготовка записей MCYT и Pointer Events

API принимает JSON с точками; исходные `.fpg` и браузерные записи необходимо преобразовать до отправки.

| Поле API | MCYT `.fpg` | Запись через Pointer Events |
| --- | --- | --- |
| `x`, `y` | Первые два канала без изменений | `x`, `y` вашей записи |
| `pressure` | Третий канал, делённый на 1023 | `pressure` |
| `azimuth` | Четвёртый канал, градусы | `azimuthAngle × 180 / π` |
| `altitude` | Пятый канал, градусы | `altitudeAngle × 180 / π` |
| `time_ms` | `index × 1000 / sampling_rate_hz`, индекс от нуля | Время точки минус время первой точки |

При частоте 100 Гц шаг времени равен 10 мс. Для браузерных записей сохраняйте фактические интервалы; приводить их к 100 Гц не нужно. Браузерные углы передаются в радианах и требуют перевода в градусы согласно [спецификации Pointer Events](https://www.w3.org/TR/pointerevents3/#dom-pointerevent-altitudeangle).

Поля браузерной записи, отсутствующие в контракте (`phase`, `stroke`, `userAgent` и другие), удалите перед отправкой.

## Ошибки

| Статус | Значение |
| --- | --- |
| 401 | API-ключ отсутствует или недействителен |
| 403 | Доступ запрещён |
| 404 | Эталон отсутствует или принадлежит другому интегратору |
| 409 | Имя интегратора уже занято |
| 422 | Некорректные параметры запроса, непригодные образцы или неподдерживаемая версия эталона |
| 500 | Внутренняя ошибка сервиса |
| 503 | Сервис временно недоступен |

Ответ об ожидаемой ошибке содержит поле `detail`. Например:

```json
{
  "detail": "Эталон не найден."
}
```

Для внутренних ошибок (`500`) возможен текстовый ответ `Internal Server Error`.

При ошибках проверки входных данных `detail` может содержать массив описаний ошибок с указанием поля. Клиенту следует ориентироваться на HTTP-статус и учитывать разные формы `detail`, не привязываясь к точному тексту сообщения.
